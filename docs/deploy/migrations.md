# Миграции БД на проде

## Что произошло 2026-09-11

При входе на сайт падало `PrismaClientKnownRequestError P2021: The table
`public.session` does not exist`. Таблицу создаёт миграция
`prisma/migrations/20260811120000_add_session_and_otp_attempts` (серверное
хранилище сессий, HIGH-2) — в репозитории она была, на проде применена не была.

Причина: в рамках HIGH-5 из `Dockerfile` убрали выполнение миграций на этапе
сборки (правильно — сборке не нужен доступ к боевой БД), но обещанный «отдельный
шаг деплоя» в Coolify так и не появился. Код уехал на прод, схема — нет.

## Что произошло 2026-09-15

Деплой `b7f4ea3` упал на сборке:

```
The column `user.city` does not exist in the current database.
  at getPostBySlug (src/features/post/services/post-services.ts:58)
Export encountered an error on /(public)/[slug]/page: /peshhera-sezam, exiting the build.
```

Колонку добавляет `20260912135255_add_guide_cabinet_fields` — она была
в репозитории и ждала своего `migrate deploy` при старте контейнера. Но старт
не наступил: `next build` пререндерит ~860 страниц **запросами в боевую БД**
(Coolify отдаёт `DATABASE_URL` и на этап сборки — дописывает `ARG`/`ENV`
в Dockerfile перед `docker build`, в логе это видно по «transferring
dockerfile: 4.98kB» при 1.5 kB в репозитории). Схема отставала от кода,
пререндер упал, контейнер до миграций не дожил.

Ловушка общая для любой миграции, добавляющей колонку в `user`, `post` или
`tour`: страницы читают модель целиком (`include: { user: true }`), поэтому
Prisma перечисляет в `SELECT` все колонки новой схемы.

Починено порядком: `prisma migrate deploy` выполняется в builder-стадии
**до** `next build`. Подробности и расплата — в комментарии у самой команды
в [`Dockerfile`](../../Dockerfile).

**Следствие для новых миграций:** они должны быть обратно совместимы. Между
`migrate deploy` на сборке и переключением трафика на новый контейнер проходит
минута-полторы, и всё это время старый код работает с новой схемой. Добавление
колонок и таблиц безопасно; переименование и удаление — только через
expand-contract (сначала добавить и начать писать в обе, выкатить, потом
удалить старое отдельным деплоем).

## Как устроено сейчас

`CMD` в [`Dockerfile`](../../Dockerfile) выполняет `prisma migrate deploy` перед
`next start` — вторым рубежом, на случай отката на старый образ, рестарта без
пересборки и повторной сборки того же коммита (тогда слой с миграцией берётся
из кеша BuildKit и не выполняется). Это значит:

- миграции применяются автоматически при каждом деплое;
- уже применённые пропускаются, повторный запуск безопасен;
- Prisma берёт advisory-lock в БД — параллельный старт контейнеров не гонка;
- если миграция падает, контейнер не поднимается и Coolify оставляет работать
  старый — приложение никогда не стартует поверх несовместимой схемы.

CLI `prisma` лежит в образе: `npm ci` ставит и devDependencies, а runner-стадия
копирует весь `/app` из builder. `prisma/` и `prisma.config.ts` не попадают
в `.dockerignore`. `DATABASE_URL` берётся из переменных окружения Coolify.

## Ручное применение (hotfix без пересборки)

```sh
ssh root@185.73.126.199
docker exec -it i4wwk40sc0s0wg0ocg4sg4sc sh
./node_modules/.bin/prisma migrate status   # сначала посмотреть, что разъехалось
./node_modules/.bin/prisma migrate deploy
```

Имя контейнера могло смениться — актуальное искать через `docker ps`.

**Перед первым `migrate deploy` обязательно посмотреть `migrate status`.** Если
боевая БД когда-то обновлялась через `prisma db push` или ручным SQL, таблица
`_prisma_migrations` не знает про часть истории, и `deploy` попытается накатить
старые миграции на уже существующие таблицы — упадёт с `P3009`/`42P07`. Лечится
`prisma migrate resolve --applied <имя_миграции>` для каждой расхождения, а не
правкой миграций.

## Чеклист при добавлении миграции

1. `npm run db:migrate:dev` локально — миграция появляется в `prisma/migrations/`.
2. Коммитить каталог миграции **вместе** с изменением `prisma/models/*.prisma`.
3. Убедиться, что миграция обратно совместима со старым кодом (см. 2026-09-15):
   добавление — да, переименование и удаление — только expand-contract.
4. Ничего отдельно на сервере делать не нужно — деплой применит сам.
