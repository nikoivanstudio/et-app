Пример: репозиторий с замоканной БД


jest.mock('@/shared/lib/db', () => ({
  dbClient: { post: mockPost }
}));

test('getPosts ensures include.user is set', async () => {
  mockPost.findMany.mockResolvedValue([{ id: 1 }]);
  await postRepositories.getPosts({ where: { published: true } });

  const calledWith = mockPost.findMany.mock.calls[0][0];
  expect(calledWith.where).toEqual({ published: true });
  expect(calledWith.include).toMatchObject({ user: true });
});

Тест проверяет контракт с Prisma без реального обращения к БД — быстро и детерминированно.

Уровень 2 — Компонентные точечно

Рендер React-компонента в jsdom и проверка поведения через роли доступности, как видит пользователь.

  • form-dialog-layout.test.tsx
  • иконка-триггер оборачивается в кликабельный button
  • проверка через getByRole('button')

render(
  <FormDialog
    {...baseProps}
    triggerButton={<Pencil data-testid="edit-icon" />}
  />
);

const trigger = screen.getByRole('button');
expect(trigger).toContainElement(
  screen.getByTestId('edit-icon')
);

Сильная практика: тест ориентирован на доступность (a11y), а не на детали реализации.

Уровень 3 — E2E (Playwright) зона роста

Что хорошо

  • Playwright настроен на 3 браузера
  • Есть trace на ретраях, HTML-репорт
  • Есть baseURL через env

Что мешает

  • 1 реальный тест (home.spec) — записанный, хрупкий (кнопка «Hellow», aria-snapshot)
  • 2 файла — boilerplate (playwright.dev)
  • webServer закомментирован
  • E2E не запускается в CI

Вывод: фундамент есть, но осмысленного E2E-покрытия бизнес-сценариев пока нет — идеальный момент заходить с BDD «с чистого листа».

Быстрая обратная связь на каждый push — хорошая база, которую стоит расширить.

Сильные стороны текущего подхода

Многоуровневость

Покрыты все 3 уровня пирамиды — есть на чём строить.

Быстрая обратная связь

Юнит-тесты мгновенные, гоняются в CI на каждый push.

Изоляция

БД мокается → тесты детерминированы, не зависят от окружения.

Тесты «как пользователь»

Testing Library + Playwright опираются на роли/a11y, а не на разметку.

Кросс-браузерность

Playwright из коробки: Chromium, Firefox, WebKit.

Структура FSD

Тесты лежат рядом с кодом фичи → легко поддерживать.

Пробелы (зоны роста)

  • E2E-сценарии бизнеса не покрыты: заявка на тур, OTP-логин, публикация поста, загрузка файлов
  • Компонентные тесты и E2E не входят в CI
  • Нет порога покрытия (coverage gate) и отчёта о покрытии в пайплайне
  • Единственный E2E хрупкий (записан рекордером, содержит отладочные артефакты)
  • Нет общих паттернов для E2E: Page Objects, фикстуры авторизации, сид данных

Именно сюда логично направить внедрение Gherkin + Playwright.

Gherkin + Playwright

Насколько применимо · что даёт · сколько стоит

Что такое Gherkin / BDD

Сценарии на «человеческом» языке Given / When / Then, понятные не только разработчикам.

Каждый шаг привязан к коду (step definition), который под капотом дёргает Playwright.

  • Единый язык бизнеса и разработки
  • Спецификация = живой тест

Функция: Заявка на тур

  Сценарий: Посетитель отправляет заявку
    Дано открыта страница тура "Гора Ай-Петри"
    Когда я заполняю имя и телефон
    И нажимаю "Отправить заявку"
    Тогда я вижу подтверждение
    И заявка появляется в дашборде гида

Применимо ли к et-app?

Да — технически легко, ценность зависит от процесса. Playwright уже стоит; E2E-слой почти пустой → внедряем без миграции легаси.

За

  • Чёткие бизнес-сценарии: заявка на тур, OTP-логин, CMS-посты, файлы, права ролей
  • Документация = тесты (онбординг, ТЗ)
  • Старт с нуля → нет затрат на переписывание

Осторожно

  • BDD окупается, если сценарии реально читают не-разработчики
  • Лишний слой абстракции (шаги) для маленькой команды
  • Дисциплина: переиспользуемые шаги, иначе хаос

Чем связать Gherkin и Playwright

playwright-bdd ⭐@cucumber/cucumber
Раннернативный Playwright Testотдельный раннер Cucumber
Параллельность / трейсы / репортыиз коробки PWнужно настраивать
Фикстуры PWдаограниченно
Зрелостьактивная, под PWклассика BDD

Рекомендация: playwright-bdd — сохраняем всю мощь Playwright (параллель, trace viewer, HTML-репорт) и получаем Gherkin сверху.

Было: записанный E2E


test('test of Home page', async ({ page }) => {
  await page.goto('http://localhost:3000/');
  await page.getByRole('button', { name: 'Hellow' }).click();
  await page.getByText('nikolaenko_i').click();
  await expect(page.locator('html')).toMatchAriaSnapshot(`...`);
});

Стало: feature + переиспользуемые шаги


// steps/home.steps.ts
Given('открыта главная страница', async ({ page }) =>
  page.goto('/'));
Then('виден переключатель темы', async ({ page }) =>
  expect(page.getByRole('button', { name: 'Переключатель темы' }))
    .toBeVisible());

Оценка трудозатрат

ЭтапСодержаниеСрок
1. Setupplaywright-bdd, структура папок, webServer, сид тестовой БД0.5–1 день
2. ПаттерныPage Objects, фикстура авторизации (storageState), общие шаги1–2 дня
3. Ключевые сценарии5–6 потоков: заявка на тур, OTP-логин, посты, файлы, права3–5 дней
4. CIотдельный job: запуск приложения + E2E + артефакты~1 день

Технический запуск BDD

~2–3 дня — Gherkin «бегает», есть демо-сценарий

Рабочее покрытие ядра

~1.5–2 недели — основные пути под автотестами + CI

Рекомендация

  1. Внедрять стоит — низкий порог входа (Playwright уже есть), E2E-слой пустой.
  2. Инструмент — playwright-bdd.
  3. Начать с PoC за 2–3 дня: 1 сценарий «заявка на тур» end-to-end + шаблон шагов.
  4. Параллельно — добавить E2E и компонентные тесты в CI отдельным job.
  5. Решение о масштабировании BDD принять после PoC: реально ли сценарии читают бизнес/QA.

Если читателей-нетехнарей нет — можно остаться на «чистом» Playwright; ценность Gherkin тогда ниже, а накладные расходы те же.

Итого

  • Тесты есть на всех 3 уровнях; сильный юнит-слой, слабый E2E
  • Gherkin + Playwright применимы — и заходить удобно сейчас
  • PoC: ~2–3 дня · рабочее покрытие ядра: ~1.5–2 недели
